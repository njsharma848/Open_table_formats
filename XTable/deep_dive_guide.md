## Why Apache XTable?

### The Open Table Format Fragmentation Problem

As data lakehouses matured, three dominant open table formats emerged — **Apache Iceberg**, **Delta Lake**, and **Apache Hudi**. Each is powerful. Each is incompatible with the others.

Organizations that standardized on one format discovered a painful reality:

| Scenario | The Pain |
|---|---|
| **Acquired a company using a different format** | Can't query their data without migration |
| **Cloud vendor only supports one format** | AWS Athena prefers Iceberg; Databricks is Delta-native |
| **Analytics team uses Trino (Iceberg-native)** | Can't read Hudi tables the data engineering team writes |
| **Migrating from Delta to Iceberg** | Petabytes of data require a full rewrite — weeks of work |
| **Multi-cloud strategy** | Different clouds, different preferred formats — data silos |
| **Vendor lock-in concerns** | Committed to Delta but want optionality to switch |

```
Without XTable — Format Silos:

  Flink Job ──▶ Hudi Table          ──▶ Only Hudi-compatible engines
  Spark Job ──▶ Delta Table         ──▶ Only Delta-compatible engines
  Batch Job ──▶ Iceberg Table       ──▶ Only Iceberg-compatible engines

  Result: 3 copies of data, 3 pipelines, 3 formats to maintain
```

```
With XTable — Format Interoperability:

  Flink Job ──▶ Hudi Table (source of truth)
                     │
               XTable Sync
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
    Iceberg       Delta     (future
    metadata      metadata   formats)
          │          │
    Trino /      Databricks /
    Athena        Power BI
                    
  Result: 1 copy of data, 1 write pipeline, all engines served
```

### What Apache XTable Is

Apache XTable (formerly **OneTable**, incubated at Apache in 2024) is a **metadata translation layer** — not a new table format. It reads the metadata of a source table (Hudi, Iceberg, or Delta) and generates equivalent metadata in one or more target formats, pointing at the **same underlying Parquet data files**. No data is copied. No ETL is run. Only metadata is translated.

> Originally built by **Onehouse** (founded by Hudi creator Vinoth Chandar), open-sourced as **OneTable**, and donated to the Apache Software Foundation as **Apache XTable** in 2024.

## Key Features

### 1. Metadata-Only Translation (Zero Data Copy)

XTable never touches your data files. It reads partition layouts, file lists, schema, and statistics from the source format's metadata and writes equivalent metadata structures for the target formats — all pointing to the same Parquet files on object storage.

```
Source: Hudi table
  data/
    part-00001.parquet   ← Never moved, never copied
    part-00002.parquet   ← Never moved, never copied

After XTable sync:
  _delta_log/            ← Generated by XTable (Delta metadata)
    00000.json
  metadata/              ← Generated by XTable (Iceberg metadata)
    v1.metadata.json
  .hoodie/               ← Original Hudi metadata (unchanged)
    hoodie.properties

All three sets of metadata point to the SAME .parquet files
```

---

### 2. Bidirectional Sync (Any Source → Any Target)

XTable supports conversion between all three major formats in any direction:

| Source Format | Supported Targets |
|---|---|
| Apache Hudi | Iceberg, Delta Lake |
| Apache Iceberg | Hudi, Delta Lake |
| Delta Lake | Hudi, Iceberg |

```yaml
# XTable configuration — convert Hudi table to both Iceberg and Delta
sourceFormat: HUDI
targetFormats:
  - ICEBERG
  - DELTA

datasets:
  - tableBasePath: s3://my-bucket/hudi/orders
    tableName: orders
    partitionSpec: "order_date:VALUE"
```

---

### 3. Incremental Sync (Not Full Re-Translation Every Time)

XTable tracks the last synced commit/snapshot and translates only the **delta** since the last sync — not the full table history. This makes continuous sync efficient even on large, active tables.

```
Timeline:

Hudi commit t=100  ──▶  XTable sync (full baseline)    ──▶  Iceberg snapshot 1
Hudi commit t=101  ──▶  XTable incremental sync        ──▶  Iceberg snapshot 2 (only new files)
Hudi commit t=102  ──▶  XTable incremental sync        ──▶  Iceberg snapshot 3 (only new files)

XTable state file: remembers last synced commit = t=101
                   next run only processes t=102 delta
```

---

### 4. Schema Synchronization

XTable translates the table schema — including column names, data types, nullability, and nested structures — across format-specific schema representations.

```
Hudi schema (Avro):          Iceberg schema:          Delta schema:
{                            schema {                  StructType [
  "name": "order_id",          1: order_id:              StructField("order_id",
  "type": "long"               required long,              LongType),
}                              2: amount:                StructField("amount",
                               optional double             DoubleType)
                             }                         ]

XTable translates between all three representations automatically
```

---

### 5. Partition Spec Translation

Each format represents partitioning differently. XTable handles the translation:

```
Hudi:    Partitioned by directory structure  →  /order_date=2024-01-15/
Iceberg: Partitioned by transform            →  days(order_date)
Delta:   Partitioned by column value         →  partitionBy("order_date")

XTable maps between these representations preserving partition pruning semantics
```

---

### 6. Catalog Integration

XTable can register the translated table in catalog systems so engines can discover it without manual configuration:

```yaml
# Register translated Iceberg table in AWS Glue
catalogImpl: org.apache.iceberg.aws.glue.GlueCatalog
catalogName: glue

# Register translated Delta table in Databricks Unity Catalog  
catalogImpl: io.delta.standalone.catalog.DeltaCatalog
catalogName: unity
```

---

### 7. Standalone JAR + Programmatic API

XTable ships as a standalone JAR for one-off or scheduled sync, and as a Java/Scala API for embedding in existing pipelines.

```bash
# One-shot sync via standalone JAR
java -jar xtable-utilities-0.2.0-bundled.jar \
  --datasetConfig my-sync-config.yaml

# Schedule via cron or Airflow for continuous sync
# Runs incrementally — only processes new commits since last sync
```

---

### 8. Metadata Statistics Preservation

XTable carries over **file-level statistics** (min/max values, null counts, row counts) from the source format into the target format's metadata. This ensures query engines can still perform **data skipping** on translated tables — not just read correctness, but read performance.

```
Hudi manifest entry:
  file: part-001.parquet
  stats: { minVal: {order_id: 1}, maxVal: {order_id: 1000}, rowCount: 5000 }

XTable translates to Iceberg manifest:
  file: part-001.parquet  (same file, same path)
  stats: { lower_bound: {1: 1}, upper_bound: {1: 1000}, row_count: 5000 }

Trino can now prune files using Iceberg metadata — same efficiency as a native Iceberg table
```

## Architecture Internals

### High-Level Translation Pipeline

```
┌──────────────────────────────────────────────────────────────────┐
│                         Apache XTable                            │
│                                                                  │
│  ┌─────────────┐    ┌──────────────────┐    ┌─────────────────┐ │
│  │  Source     │    │  Internal        │    │  Target         │ │
│  │  Reader     │───▶│  Canonical       │───▶│  Writer(s)      │ │
│  │             │    │  Representation  │    │                 │ │
│  │ HudiSource  │    │  (format-        │    │ IcebergTarget   │ │
│  │   Reader    │    │   agnostic)      │    │ DeltaTarget     │ │
│  │ IcebergSrc  │    │                  │    │ HudiTarget      │ │
│  │   Reader    │    │  - Schema        │    │                 │ │
│  │ DeltaSource │    │  - Partitions    │    │                 │ │
│  │   Reader    │    │  - File list     │    │                 │ │
│  └─────────────┘    │  - Stats         │    └─────────────────┘ │
│                     │  - Snapshots     │                        │
│                     └──────────────────┘                        │
└──────────────────────────────────────────────────────────────────┘
```

### Canonical Representation (The Internal Model)

XTable converts source metadata into a **format-agnostic internal model** before generating target metadata. This is what makes bidirectional translation possible without N×M format-specific converters:

```
Source formats  ──▶  Internal Canonical Model  ──▶  Target formats

Hudi   ─┐                                          ┌─▶  Iceberg
Iceberg ─┼──▶  OneTable Schema                     ├─▶  Delta
Delta  ─┘      OneTable Partition Spec    ──────────┤
               OneTable DataFile          ──────────┴─▶  Hudi
               OneTable Snapshot
```

### Sync State Tracking

XTable maintains a **sync state file** alongside the table to track incremental progress:

```
s3://my-bucket/hudi/orders/
├── .hoodie/                    ← Hudi metadata (source of truth)
├── _delta_log/                 ← Generated by XTable
├── metadata/                   ← Generated by XTable (Iceberg)
└── .xtable/
    └── sync_state.json         ← XTable state: last synced commit per target format
```

```json
// sync_state.json
{
  "ICEBERG": {
    "lastSyncedSourceCommit": "20240115143022",
    "lastSyncedTargetSnapshotId": 4567890123
  },
  "DELTA": {
    "lastSyncedSourceCommit": "20240115143022",
    "lastSyncedDeltaVersion": 42
  }
}
```

### File Layout After Full Sync

```
s3://my-bucket/source-table/                  (Hudi as source of truth)
│
├── .hoodie/                                  ← Hudi metadata
│   ├── hoodie.properties
│   ├── 20240115143022.commit
│   └── .hoodie_partition_metadata
│
├── order_date=2024-01-15/                    ← Actual data files
│   └── part-00001-abc.parquet               ← Shared by ALL formats
├── order_date=2024-01-16/
│   └── part-00002-def.parquet               ← Shared by ALL formats
│
├── _delta_log/                               ← XTable-generated Delta metadata
│   ├── 00000000000000000000.json
│   └── 00000000000000000001.json
│
└── metadata/                                 ← XTable-generated Iceberg metadata
    ├── v1.metadata.json
    └── snap-xxx.avro
```

### Translation Workflow (Step by Step)

```
Step 1: XTable reads source metadata
        └─▶ Hudi: reads .hoodie/timeline, partition metadata, file groups
        └─▶ Iceberg: reads metadata.json, manifest lists, manifests
        └─▶ Delta: reads _delta_log/ JSON entries and checkpoints

Step 2: XTable builds internal canonical snapshot
        └─▶ Schema (format-agnostic column definitions)
        └─▶ Partition layout (directories → partition specs)
        └─▶ File list (paths, sizes, row counts, min/max stats)
        └─▶ Snapshot timeline (commit timestamps)

Step 3: XTable writes target metadata
        └─▶ For Iceberg: writes manifest files, manifest list, metadata.json
        └─▶ For Delta: writes _delta_log/ JSON entries with add/remove actions
        └─▶ For Hudi: writes .hoodie/ timeline and metadata table entries

Step 4: XTable updates sync state
        └─▶ Records last synced commit in .xtable/sync_state.json

Step 5: (Optional) Catalog registration
        └─▶ Registers new snapshot in Glue / HMS / Unity Catalog
```

### Programmatic API (Java)

```java
import org.apache.xtable.conversion.ConversionConfig;
import org.apache.xtable.conversion.ConversionController;
import org.apache.xtable.model.storage.TableFormat;

// Define the source table
SourceTable sourceTable = SourceTable.builder()
    .name("orders")
    .basePath("s3://my-data-lake/hudi/orders")
    .formatType(TableFormat.HUDI)
    .partitionSpec(PartitionSpec.of(
        PartitionField.of("order_date", PartitionTransformType.VALUE)
    ))
    .build();

// Define target formats
ConversionConfig config = ConversionConfig.builder()
    .sourceTable(sourceTable)
    .targetFormats(Arrays.asList(TableFormat.ICEBERG, TableFormat.DELTA))
    .build();

// Run the sync
ConversionController controller = new ConversionController(hadoopConf);
controller.sync(config, SyncMode.INCREMENTAL);
```

## Use Case Scenarios

### 1. Multi-Engine Data Platform (One Table, Every Engine)

**Scenario:** A large org has Databricks (prefers Delta), AWS analytics (prefers Iceberg/Athena), and a real-time Flink pipeline (writes Hudi). Three teams, three formats, same data.

```
Flink Pipeline  ──▶  Hudi Table (S3)  ──▶  XTable Sync (every 10 min)
                                                     │
                                     ┌───────────────┼───────────────┐
                                     ▼               ▼               ▼
                               Iceberg meta     Delta meta      (Hudi native)
                                     │               │               │
                               AWS Athena     Databricks        Flink CDC
                               Trino          Power BI          Reader
                               Snowflake      Delta Live        (no sync needed)
                                              Tables
```

**Result:** One write pipeline, zero data copies, all engines served.

---

### 2. Zero-Downtime Format Migration (Delta → Iceberg)

**Scenario:** An org wants to migrate 200 TB of Delta tables to Iceberg to reduce Databricks dependency — without a multi-week rewrite and without downtime for consumers.

```
Phase 1 (Day 1):     XTable translates Delta → Iceberg metadata
                     Iceberg consumers can now read the same data
                     Delta consumers continue working unchanged

Phase 2 (Weeks 1–4): Migrate write pipelines from Delta to Iceberg one by one
                     XTable now translates Iceberg → Delta (reversed)
                     Delta consumers continue working during migration

Phase 3 (Week 5):    All pipelines writing Iceberg natively
                     Delta consumers migrated to Iceberg
                     XTable sync decommissioned
                     200 TB migrated — zero rewrite, zero downtime
```

---

### 3. Post-Acquisition Data Integration

**Scenario:** A company acquires a startup. The acquirer uses Iceberg; the startup uses Hudi. The deal closes in 30 days. The data team has 30 days to integrate data access.

```
Startup's S3 bucket:
  └── hudi/transactions/    ← startup writes here

XTable sync (deployed in hours):
  └── metadata/             ← Iceberg metadata generated for same files

Acquirer's Trino cluster:
  SELECT * FROM iceberg.startup.transactions
  -- Reads the startup's Hudi data via Iceberg metadata
  -- No data moved, no pipelines rebuilt in 30 days
```

---

### 4. Hybrid Cloud / Multi-Cloud Interoperability

**Scenario:** Data is written in Hudi on AWS (where Hudi tooling is strong), but the analytics team queries via Google BigQuery (which only supports Iceberg via BigLake).

```
AWS:
  Flink + EMR ──▶ Hudi Table (S3)
                       │
                  XTable Sync
                       │
                  Iceberg metadata (same S3 location)

GCP:
  BigQuery BigLake ──▶ reads Iceberg metadata on S3
                   ──▶ queries Parquet files directly
                   (no data replication to GCS needed)
```

---

### 5. Eliminating the Lambda Architecture

**Scenario:** A company runs two parallel pipelines — a Flink Hudi streaming pipeline for real-time data and a Spark batch pipeline writing Delta for historical data. They want to serve both from one table without a union query.

```
Before (Lambda):
  Flink ──▶ Hudi (real-time layer)   ──▶  UNION query at serving time
  Spark ──▶ Delta (batch layer)      ──▶  (complex, expensive)

After (XTable):
  Flink ──▶ Hudi (source of truth, unified)
                  │
            XTable Sync
                  │
            Delta metadata
                  │
  Spark batch jobs read from Delta metadata — same Hudi data
  No UNION, no dual pipeline, no reconciliation
```

---

### 6. Vendor Lock-In Insurance

**Scenario:** A company is on Databricks and all tables are Delta. They want to hedge against Databricks pricing increases by ensuring they could move to open-source Trino + Iceberg at any time — without committing to a migration now.

```
Current state:
  Databricks ──▶ Delta tables (S3)

XTable shadow sync (background job):
  Delta tables ──▶ XTable ──▶ Iceberg metadata (same S3 location)

Validation:
  Trino cluster (dev env) reads Iceberg metadata — validates parity

If/when migration is needed:
  Flip the switch — point Trino at Iceberg metadata
  Decommission Databricks
  Zero data rewrite needed
```

## Pros and Cons

### ✅ Pros

| Advantage | Detail |
|---|---|
| **Zero data duplication** | Only metadata is generated — no Parquet files are copied or rewritten |
| **Zero-downtime migration** | Translate metadata first; migrate writers later; consumers never experience downtime |
| **Engine agnosticism** | Any engine that reads Iceberg, Delta, or Hudi can access the same data |
| **Eliminates data silos** | Different teams using different engines can collaborate on the same table |
| **Low operational cost** | A lightweight JAR + a YAML config — minimal infrastructure to run |
| **Incremental sync** | Tracks last synced commit; subsequent syncs are fast and cheap |
| **Statistics preservation** | Carries over file-level min/max stats for data skipping — not just correctness, but performance |
| **Vendor lock-in insurance** | Keep Delta as source of truth but maintain Iceberg metadata as an escape hatch |
| **No changes to consumers** | Existing engines reading Iceberg/Delta/Hudi don't need any changes |
| **Apache-governed** | Vendor-neutral governance under the Apache Software Foundation |
| **Bidirectional** | Convert in any direction — not locked into one-way translation |

---

### ❌ Cons

| Disadvantage | Detail |
|---|---|
| **Not a table format** | XTable solves interoperability — it doesn't replace the need to choose a primary format |
| **Sync latency** | Translated metadata is always slightly behind the source (sync interval = freshness lag) |
| **Operational overhead** | Requires a sync job scheduler (Airflow, cron, Spark job) to run continuously |
| **Partial feature parity** | Not all features of the source format translate cleanly (e.g., Hudi's MoR delete semantics don't map 1:1 to Iceberg v2 delete files) |
| **No DML on translated tables** | Target-format metadata is read-only — writes must go through the source format only |
| **Young project** | Donated to Apache in 2024; ecosystem, documentation, and community still maturing |
| **Schema evolution lag** | Complex schema changes in the source may require a full re-sync rather than incremental |
| **No real-time sync** | Sync runs on a schedule (minutes); not suitable for sub-minute freshness requirements |
| **Limited catalog support** | Catalog registration support (Glue, HMS) is present but Unity Catalog and Nessie integrations are maturing |
| **Debug complexity** | When translated metadata diverges from source, diagnosing root cause requires understanding three format internals |
| **Hudi-centric history** | Built by the Hudi creators; Hudi-as-source is most mature; Iceberg-as-source and Delta-as-source are newer and less battle-tested |

## FAANG / MAANG Interview Questions

### 🔵 Conceptual & Fundamentals

**Q1. What is Apache XTable and what fundamental problem does it solve?**

> Apache XTable (formerly OneTable) is a **metadata translation layer** for open table formats. It solves the **format fragmentation problem** in data lakehouses: organizations that use Hudi, Iceberg, and Delta Lake in different parts of their stack cannot query data across formats without duplicating data or rebuilding pipelines.
>
> XTable reads the metadata of a source table (Hudi, Iceberg, or Delta) and generates equivalent metadata in one or more target formats, all pointing at the **same underlying Parquet data files**. No data is moved or copied. The result: a single table readable by every engine that supports any of the three formats.

---

**Q2. How does XTable work without copying data? What exactly does it translate?**

> XTable translates only **metadata** — never data files. It reads the source format's metadata structures (Hudi's `.hoodie/` timeline, Iceberg's `metadata.json` + manifests, Delta's `_delta_log/`) and generates the equivalent structures for target formats in the same table directory.
>
> Specifically, XTable translates:
> - **Schema:** column names, types, nullability, nesting — across Avro (Hudi), Iceberg schema IDs, and Delta's StructType
> - **Partition spec:** directory-based partition paths → format-specific partition representations
> - **File list:** paths, sizes, row counts, and per-column min/max statistics — from source manifest to target manifest
> - **Snapshot/commit timeline:** source commits → target snapshot entries
>
> All generated metadata files point to the **same Parquet file paths** as the source. A Trino query reading XTable-generated Iceberg metadata reads the exact same bytes as a Spark query reading the original Hudi metadata.

---

**Q3. What is the canonical internal representation in XTable and why is it important?**

> To avoid building N×M format-specific converters (Hudi→Iceberg, Hudi→Delta, Delta→Hudi, Delta→Iceberg, etc.), XTable uses a **format-agnostic canonical model** as an intermediate representation.
>
> Every source reader (HudiSourceReader, IcebergSourceReader, DeltaSourceReader) converts source metadata into this single internal model:
> - `OneTableSchema` — format-agnostic column definitions
> - `OneTablePartitionSpec` — format-agnostic partition layout
> - `OneTableDataFile` — format-agnostic file entry with stats
> - `OneTableSnapshot` — format-agnostic snapshot/commit
>
> Every target writer (IcebergTargetWriter, DeltaTargetWriter, HudiTargetWriter) consumes this canonical model and produces target-format metadata.
>
> This reduces the problem from O(N²) converters to O(N) readers + O(N) writers — a fundamental architectural decision that makes adding new formats tractable.

---

**Q4. What is incremental sync in XTable and how does it work?**

> On the first run, XTable performs a **full baseline sync** — it reads the entire source table metadata and generates complete target metadata.
>
> On subsequent runs, XTable reads the **sync state file** (`.xtable/sync_state.json`) to find the last synced source commit for each target format. It then reads only the source commits/snapshots **newer than** the last synced state and generates incremental metadata updates for the targets.
>
> For example, if a Hudi table has 1000 commits and XTable last synced at commit 990, the next run only processes commits 991–1000. This is critical for production use where tables receive continuous writes — without incremental sync, each run would re-translate petabytes of metadata.

---

**Q5. Can you write to a Delta table that was created by XTable translating a Hudi source?**

> **No.** XTable generates **read-only** target metadata. The translated Delta or Iceberg metadata is for **read access only**. All writes must go through the **source format** (Hudi in this example).
>
> If a writer tried to write to the XTable-generated Delta metadata directly, it would create a Delta commit that modifies data files — but the Hudi metadata would have no knowledge of this change. The two metadata stores would immediately diverge, causing data corruption and inconsistency.
>
> **The pattern is:** one writer, one source format, one source of truth. XTable provides read-only views of that source truth in other formats.

---

**Q6. What are the limitations of metadata translation? What can XTable NOT translate?**

> Translation is not always lossless. Key limitations:
>
> - **Hudi MoR (Merge-on-Read) semantics:** Hudi's delta log files (avro-encoded change logs) don't have a direct equivalent in Iceberg or Delta. XTable exposes the **compacted read-optimized view** to target formats — meaning uncommitted MoR changes may not be visible in translated metadata until compaction.
> - **Format-specific features:** Hudi's incremental queries, Iceberg's branching/tagging, Delta's Change Data Feed — these are source-format features with no target-format equivalent. XTable translates the core read view, not every feature.
> - **Real-time sync:** XTable runs on a schedule (minutes). It cannot provide the millisecond-level freshness that a native format write provides.
> - **Complex schema evolutions:** certain schema changes (column reordering, type changes beyond widening) may require a full re-sync.
> - **Catalog-level features:** table properties, access controls, and catalog-specific metadata don't always map cleanly across formats.

**Q7. How would you architect a continuous XTable sync pipeline in production?**

> - Store sync state in S3 alongside the table (`.xtable/sync_state.json`) for durability

> - Use **catalog registration** (Glue, HMS) so new snapshots are automatically visible to Athena/Trino without manual refresh

**Q8. How does XTable handle the small-file problem? Does it exacerbate it?**

> XTable itself does **not create or modify data files** — so it cannot directly cause small-file problems. However, it faithfully translates whatever file layout exists in the source.
>
> If the source table has a small-file problem (common in Hudi/Iceberg streaming tables), the translated metadata will expose the same small files to target-format readers. The number of files in the manifest will be high, causing slow metadata scans and high per-file overhead in target engines.
>
> **The correct mitigation:** solve the small-file problem in the **source format** first (Hudi compaction, Iceberg `rewrite_data_files`, Paimon compaction), then XTable will translate the compacted, healthy file layout to all targets. XTable is not the right tool for compaction — it's purely a metadata layer.

**Q9. What is the freshness trade-off in XTable-translated tables and how do you manage it?**

> XTable syncs on a **schedule** — meaning target-format metadata always lags the source by at least one sync interval. If XTable runs every 10 minutes, Trino reading the Iceberg metadata could see data that is up to 10 minutes stale.
>
> **Managing freshness:**
> - **SLA alignment:** negotiate freshness SLAs with consumers. If Trino analysts can tolerate 15-minute lag, a 10-minute sync interval is fine; if they need 1-minute lag, consider whether XTable is the right tool.
> - **Event-driven sync:** instead of cron, trigger XTable on Hudi/Iceberg commit events (e.g., S3 event notifications → Lambda → XTable job) for near-real-time sync.
> - **Source-format priority:** route time-critical queries to the **source format** directly (e.g., Flink reads Hudi natively). Only route analytical/ad-hoc queries through translated metadata.
> - **Monitoring:** expose `last_sync_timestamp` as a metric; alert when lag exceeds the SLA threshold.

**Q10. How would you use XTable to execute a zero-downtime migration from Delta to Iceberg?**

> **Phase 1 — Enable parallel reads (Day 1, zero risk):**

> - Migrate remaining Delta consumers to Iceberg
> - Stop XTable sync
> - Delete Delta metadata (`_delta_log/`)
> - Zero bytes of Parquet data were ever copied or rewritten

**Q11. What are the consistency guarantees when XTable translates a table that is actively receiving writes?**

> XTable provides **snapshot-level consistency** for each translated state. Each XTable sync run reads a **committed, consistent snapshot** from the source (a specific Hudi commit or Iceberg snapshot) and generates target metadata reflecting exactly that snapshot.
>
> **What this means:**
> - Target readers always see a **complete, consistent state** — never a partial write
> - Target readers may see a **stale state** — the state as of the last sync, not the current source state
> - There is **no cross-format transactional guarantee** — a writer can commit to Hudi while XTable is mid-sync to Iceberg; the Iceberg reader will see the pre-write state until the next sync completes
>
> **Implication for design:** don't use XTable in workflows that require cross-engine transactional reads (e.g., "write to Hudi and immediately guarantee the Iceberg reader sees the same data"). For analytics and reporting with tolerable lag, the consistency model is sufficient.

**Q13. How would you handle a scenario where XTable-translated Iceberg metadata becomes corrupted or diverges from the Hudi source?**

> **Detection:**
> - Run periodic **reconciliation jobs** that compare row counts, partition counts, and file counts between source Hudi metadata and translated Iceberg metadata
> - Alert on divergence beyond a threshold (e.g., >0.1% row count difference)
> - Monitor XTable sync job success/failure rates in the orchestration system
>
> **Recovery options:**
> 1. **Incremental re-sync from last known good state:** delete the corrupt target metadata files, reset the sync state to a known-good commit, re-run XTable sync — it will regenerate metadata from that point forward
> 2. **Full re-sync:** delete all generated Iceberg metadata AND the sync state file. Re-run XTable with `SyncMode.FULL`. This is the nuclear option — regenerates everything from scratch. Safe for correctness, expensive for large tables.
> 3. **Snapshot rollback on target:** if the Iceberg catalog supports it, roll back the Iceberg metadata to the last verified-good snapshot ID, then re-run incremental sync
>
> **Prevention:**
> - Never manually edit XTable-generated metadata files
> - Don't allow direct writes to translated (target-format) tables
> - Version control XTable configuration YAML files
> - Test sync recovery procedures in staging regularly

**Q14. XTable vs a custom Spark ETL job for format migration — how do you make the architectural decision?**

> | Dimension | Apache XTable | Custom Spark ETL |
> |---|---|---|
> | **Data copy** | No — metadata only | Yes — reads and rewrites all Parquet files |
> | **Migration speed** | Hours (metadata only) | Days to weeks (rewrites petabytes) |
> | **Storage cost** | Minimal (only metadata files) | Doubles storage during migration |
> | **Ongoing sync** | Yes — continuous sync supported | One-time job; not designed for ongoing use |
> | **Format feature parity** | Partial — core read view only | Full — native write in target format |
> | **DML on target** | No — read-only target | Yes — fully writable after migration |
> | **Complexity** | Low — JAR + YAML config | High — custom Spark code, testing, monitoring |
> | **Risk** | Low — source untouched | High — bugs in ETL corrupt data |
>
> **Choose XTable when:** you need fast interoperability, ongoing multi-format access, zero-downtime migration, or lock-in insurance without committing to a full migration.
>
> **Choose custom Spark ETL when:** you need full feature parity in the target format (branching, CDF, MoR with delete files), the migration is one-time and permanent, or target-format DML is required from day one.

**Q15. How does XTable's canonical model handle the impedance mismatch between Hudi's row-level delete semantics and Iceberg's positional delete files?**

> This is one of XTable's hardest translation problems. Hudi MoR tables use **delta log files** (Avro-encoded change records) that record inserts, updates, and deletes as a log. Iceberg uses **positional delete files** or **equality delete files** (format v2). These are fundamentally different representations.
>
> **XTable's current approach:**
> - For **MoR tables**, XTable translates only the **read-optimized (compacted) view** — it exposes the state after Hudi's compaction has merged the delta logs back into base files. Delete records in the log are **not** translated as Iceberg delete files; instead, XTable waits until Hudi compaction removes deleted rows from the base files, then translates the clean base files.
> - **Implication:** if a Hudi MoR table has recent deletes that haven't been compacted yet, the XTable-generated Iceberg view may still show those deleted rows until the next Hudi compaction + XTable sync cycle.
>
> **Workaround:** for tables with frequent deletes requiring immediate visibility in translated formats, force Hudi inline compaction at higher frequency before XTable sync runs. For CoW tables, this problem doesn't exist — deletions are immediately materialized in the base files.
